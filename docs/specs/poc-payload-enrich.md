# POC：在 EMQX 中就地丰富消息载荷

## 问题陈述

设备上报的遥测消息里只带了设备自己的字段（比如 `device_id`、温度、时间戳），
缺少业务侧需要的上下文（比如这台设备属于哪个组织 `org_id`）。
下游订阅者拿到消息后还得自己再去查一遍设备信息，既麻烦又重复。

我们想知道：能不能让 EMQX 在消息经过时**顺手把这些上下文补进去**，
而且**不拖慢消息转发**？这是一个需要先验证可行性的问题，所以先做一个 POC。

## 解决方案

做一个 EMQX 插件，在消息发布的那一刻介入：
按 `device_id` 去一个独立的「设备注册表」服务查到该设备的 `org_id`，
把它合并进消息载荷里，订阅者直接就能收到带 `org_id` 的完整消息。

关键在于**不能让查询拖慢转发**：第一次见到某台设备时，消息照常原样放行，
查询在后台异步进行并把结果缓存起来；之后再来的消息命中缓存，直接补齐字段。
查注册表这件事无论快慢、成功失败，都不会卡住消息转发这条主路。

## 这个 POC 要证明的道理

一句话：**可以在不牺牲转发速度的前提下，在 EMQX 内部就地丰富消息。**

用一套最小的、能跑起来的环境来演示：

1. 消息能被就地改写——订阅者收到的载荷里确实多出了 `org_id`。
2. 丰富这一步足够快——每条消息的处理耗时稳定在**微秒级**，订阅者感知不到额外延迟。
3. 永不阻塞——即使注册表变慢、拒绝服务甚至宕机，消息转发依然照常、依然是微秒级，
   只是暂时查不到的设备「这次先不补、下次再补」。
4. 对缓存行为有合理交代——第一次见到的设备、以及注册表里查不到的设备，
   会被正确地分别对待（已知 / 未知），不会反复无意义地重试。

## 演示组成（概念层面，不涉及实现细节）

- 一个 **EMQX 代理**，装上这个丰富插件。
- 一个**设备注册表**服务，提供按设备查上下文的接口，并能人为注入「变慢 / 拒绝」等故障，用于验证第 3 点。
- 一个**发布端**和一个**订阅端**作为测试道具：发布端发出几条不同设备的消息，
  订阅端打印收到的内容，用来肉眼对照「哪条被补齐了、哪条没有」。

跑完一遍演示，就能同时看到「载荷被补齐」和「耗时是微秒级」这两件事，
从而证明这条路走得通。

## 明确不在范围内（留给产品化阶段）

- 缓存的过期与清理策略。
- 查询并发（本 POC 一次只查一个）。
- 「超时」与「拒绝」两类故障的差异化退避。
- 插件配置化（本 POC 参数写死）。
- 多节点集群下的缓存一致性。
- 完整的「冷 / 已知 / 未知 / 未决」状态机词汇。

这些都不影响本 POC 要证明的核心结论，因此刻意推迟。
